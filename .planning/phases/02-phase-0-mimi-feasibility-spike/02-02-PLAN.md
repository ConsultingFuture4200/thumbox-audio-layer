**Step 3 — Write `spike/src/spike/bench_vram_concurrent.py`** (~100–140 lines):

Critical implementation choices (don't substitute these silently):
  - **Don't** spawn 4 OS processes for 4 sessions. ROCm + multiprocessing has known driver-state issues. Use 4 in-process Python contexts each holding their own model copies on the same device. This is conservative (overestimates VRAM if anything), which is the right direction for a kill-criterion check.
  - Load order matters for fragmentation: load Mimi first (smallest), then adapter, then Whisper INT8, then Qwen3-4B AWQ-Int4 last (largest). Repeat 4 times. Record VRAM after each load via `torch.cuda.memory_allocated()` and `torch.cuda.max_memory_allocated()` (works on ROCm).
  - Run a warmup pass per concurrent session: encode a 1-second WAV through Mimi, transcribe through Whisper, generate 10 tokens through Qwen3-4B, project through adapter. This forces kernel allocations into VRAM that don't show up at load-time.
  - After warmup, capture `torch.cuda.max_memory_allocated()` as `peak_vram_gb`. Record per-model contribution by loading each in isolation in a separate process invocation (same script with `--isolate-model <name>` flag) and recording its solo footprint.
  - Output JSON conforming to the schema in `<behavior>` Test 3.

Strix Halo has **128 GB unified memory** but the GPU-allocatable slice is configurable via BIOS (typical: 64–96 GB). Default to 96 GB conservative for the derate; document this assumption in the JSON `notes` field.
